### 2.2 训练的对象和固定的部分

本项目优化的是语言模型根据当前观察生成动作的概率分布。训练不会自动改写 Python 工具实现、Docker 服务、测试用例或 ZzhClaw 的业务代码。

Agent 训练属于模型后训练。这里的特点是输入包含工具反馈，样本由多轮交互构成，奖励取决于最终代码是否通过验收。普通答案监督也能做多轮训练；本项目的区别应从轨迹与奖励的构造说明，而不是宣称发明了一种不同于后训练的训练类别。

## 3. SFT 怎样训练工具使用

### 3.1 为什么先增加 SFT

第七天原模型的 32 条轨迹都失败，同题候选奖励全部为 0。原始输出中有源码占位符、未知工具名、错误参数和解释性散文。此时扩大 RL 时长，仍可能反复得到没有相对差异的分组。

先排除接口和服务故障，再使用成功轨迹监督模型，是为了获得可执行的探索行为。此次 SFT 同时使用工具动作和正确修复源码，不能称为只训练 JSON 格式。

### 3.2 一条教师轨迹为什么变成五个监督样本

教师路径是：

```text
读取 solution.py → 读取 public_tests.py → 写入正确修复
→ 运行公开测试 → 输出明确的 final
```

每个模型决策都形成一个“当前完整上下文 → 下一条 assistant 响应”的监督样本。之前的动作和真实工具反馈进入上下文。

因此，本次有 63 条教师轨迹，但有 `63 × 5 = 315` 个监督样本。不能把 315 说成 315 个独立题目，也不能说成 315 条独立完整轨迹。

所有教师轨迹都先经 Docker 终局验收得到 1。模型未来推理时仍从缺陷源码开始，工具工作区里没有教师答案。

### 3.3 为什么只在 assistant 响应位置计算监督损失

一个样本可以这样理解：

```text
input_ids = [系统提示、题目、已有动作、工具反馈、待学习的 assistant 响应]
labels    = [       前面全部填 -100       、 assistant 响应 token       ]
```

`-100` 表示这些位置不作为本次监督预测目标。模型仍会读取题目和工具反馈作为条件；忽略损失不等于把它们从输入中删除。

目标是让模型学会在给定上下文后生成正确动作，不是把环境返回的测试文本当成模型应该自己编造的回答。当前脚本还核对完整聊天模板的前缀与生成提示一致，避免在错误 token 边界上训练。因果语言模型内部处理预测位置的 shift，不应重复手动错移一次。

### 3.4 LoRA 与本次参数

LoRA 用低秩增量表示权重更新，直观可写成 `W_new = W_base + scale × B × A`。训练时基座冻结，主要更新增量参数；合并后可得到常规完整模型。

本次 rank=16、alpha=32、dropout=0.05、target_modules=all-linear，学习率 1e-4，micro batch=1、梯度累积=4，进行 80 次 optimizer 更新。只检查到 28 个 q_proj 张量有变化，是保存的验证范围，不能据此说“仅训练了 28 个张量”。

每累计 4 个监督样本的梯度，调用一次 optimizer.step。因此 80 次更新共消费 320 次样本，约等于这份 315 样本数据的一轮遍历，尾部进入下一轮打乱序列；不是训练了 80 个 epochs。

### 3.5 SFT 数据怎样避免泄漏

监督只使用 train，并排除全部 8 个诊断来源。实际进入 SFT 的是 27 个 train 来源、63 个任务；dev/test 答案没有用作标签。

正确 train 修复源码可以作为监督标签交给可信训练进程。它与“把参考答案放进 Agent 可读的工具工作区”是两种不同的数据访问方式。候选执行环境只看到缺陷文件和公开测试，私有验收材料始终由 Mac 服务持有。

## 4. 多轮 Agent 轨迹怎样进入训练

### 4.1 episode、step、group 与 update

| 名称 | 含义 | 本次例子 |
|---|---|---|
| task | 一个缺陷任务 | mbpp-602-m01 |
| step | 一次模型生成及对应动作推进 | 生成 read_file 请求并获得反馈 |
| episode / trajectory | 从恢复缺陷到结束的整条尝试 | 读取、修改、测试、结束，共 5 步 |
| group | 同一道题的多个完整候选 | n=4，4 条轨迹相互比较 |
| update | 一次全局训练更新 | 4 题 × 4 候选 = 16 条轨迹进入本次更新 |

第八天 5 次更新共 80 条轨迹；由于每条多轮，实际训练 step 行数大于 80。5 次 optimizer 更新与最多 6 次 Agent 决策是不同层次的计数。

### 4.2 本项目按生成 step 建训练行

```text
step 1:
  prompt = 系统提示 + 题目
  response = 模型生成的 read_file 请求

step 2:
  prompt = 之前消息 + 真实文件内容观察
  response = 模型生成的下一条动作
```

每一行只把本轮模型生成放进 response。文件内容、测试反馈保留在下一轮 prompt；这些观察会影响后续决策，但不作为本轮模型动作 token 去优化。

本项目不把模型生成的 JSON 自动改写成另一段动作文本再当作训练 response。完整原始输出、response_ids 和工具反馈都保留，解析器仅决定是否执行。为了聊天模板衔接，下一轮消息内容只移除由模板重新添加的末尾 EOS 边界，原始训练 response_ids 仍保留生成结果。

### 4.3 三种 mask / label 不要混淆

| 项目 | 用途 | 本项目关键规则 |
|---|---|---|
| attention_mask | 指示有效输入与 padding | padding 不作为有效上下文 token |
| SFT labels=-100 | 排除监督损失位置 | 当前 prompt 和观察不作为下一响应的监督目标 |
| GRPO response_mask | 指定策略损失作用的位置 | 模型生成 token 为 1，response padding 为 0 |

在当前“一次生成一行”的设计里，工具观察根本不放进 response。其他框架也可能把整段交互拼在一个序列内并把工具 token 的响应 mask 设为 0；应以具体实现为准。

### 4.4 终止、预算与清理也是训练正确性

模型可明确输出 `{"final":"done"}` 结束；达到 6 次决策上限也会验收当前代码。若下一轮上下文超限，环境验收当前补丁，把终局奖励归到最近一次真实生成 step，不伪造一条带奖励的模型回复。

格式错误消耗一步，非法写入保留原文件。所有路径最终清理工作区。服务不可达等基础设施错误抛出异常、终止当前 rollout/batch；当前实现没有选择性过滤单条失败候选后继续凑组。

要区分：模型代码执行超时可以是有效失败；执行服务本身不可达属于基础设施无效尝试。完整 dev 评测允许同 seed 最多 2 次基础设施重试，本次未发生这类重试。

## 5. GRPO 的奖励与优势怎样计算

### 5.1 终局奖励只计一次

一条成功的五步轨迹，奖励可以是：

```text
step rewards = [0, 0, 0, 0, 1]
trajectory return = 1
```

公开测试反馈是模型观察，不重复作为额外奖励。不能把成功后的 1 回填到每一步，变成总奖励 5；否则更长轨迹会被错误地赋予更多收益。

本次终局奖励取决于受限候选是否通过全部私有验收。实际 trainer batch 中会核对环境总奖励与训练总奖励一致。

### 5.2 用真实分组手算优势

第七天一个 train 分组得到 `[1, 1, 0, 1]`。固定上游实现对同题轨迹总奖励做标准化：

```text
A_i = (R_i - 组内平均奖励) / (组内标准差 + 1e-6)
```

本实现使用 torch.std 默认的样本标准差。这个分组的均值为 0.75、标准差为 0.5，因此近似优势是 `[0.5, 0.5, -1.5, 0.5]`。

成功候选得到正的相对信号，失败候选得到负的相对信号。这里只说明优化方向；实际变化还受概率比率、clipping、KL、学习率和梯度聚合影响。

`[0,0,0,0]` 与 `[1,1,1,1]` 的奖励减均值都为零，因此该分组的策略优势为零。全部成功在任务完成上很好，却不提供本组的相对比较信号。

### 5.3 为什么先聚合轨迹，再广播到各步

本实现先按 trajectory_uids 汇总各步奖励，再按同题 uid 比较不同轨迹，最后把该轨迹的优势广播到各步模型生成 token。

这样一条成功轨迹中的读取、写入、测试等决策都能得到终局信号，而不是只训练最后一句 final。padding 不获得优势。

这仍是比较粗的信用分配：它没有精确判定某个具体步骤对成功贡献了多少。不能因为多个步骤都收到优势，就声称已经实现细粒度的因果归因。

### 5.4 策略、旧策略和 reference

Actor 是正在优化的模型；旧策略概率作为本次概率比率和 clipping 的比较基准；reference 用于 KL 约束，是不同职责。

直观上，策略项根据优势调整已采样动作的概率，clipping 限制过大的更新，KL 项约束当前策略偏离 reference 的程度。本次 reference 是固定的 SFT 起点，KL 系数为 0.001，未再把 KL 重复加进环境 reward。GRPO 未使用价值 Critic，但仍使用 reference 和规则奖励。

### 5.5 第五次为什么还有梯度

第八天第五次更新的 4 个分组全部为 1，实际 pg_loss=0、actor/kl_loss 约为 0.0005635，梯度范数约为 0.0001232。

它说明策略项没有组内相对信号，而 KL 正则项仍可产生梯度。“梯度非零”能帮助验证优化过程，不能单独证明任务奖励在有效指导这次学习。

### 5.6 实际 batch 检查比纸面公式更重要

AuditedRayAgentTrainer 在真实 `_update_actor` 前检查分组、步骤顺序、终局奖励、mask 与实际优势张量，然后委托固定上游实现更新。它没有另写一套 GRPO 替代训练算法。

需要的证据链是：正确工具轨迹 → 正确训练行 → 正确分组奖励与优势 → 有限梯度 → 权重变化 → 保存与重载。合成张量探针验证函数行为，真实 batch 检查证明训练期间确实经过了这条路径。

## 6. 评测结果应该怎样理解

### 6.1 小诊断与完整 baseline 的用途不同

第七天测 4 train + 4 dev 任务，各 4 次，temperature=0.8；它用于发现协议问题与探索奖励差异。第八天测全部 32 dev 任务，各 3 次，temperature=0.6；它用于保存完整开发集基线。

两者任务范围和采样设置不同，不能把第七天 75% 到第八天 65.63% 说成模型退化，也不能把原模型的小样本全 0 当成完整 dev 都不可能成功。

### 6.2 单次成功率与 pass@3

第八天 SFT-only 的 63/96 是所有有效单次 episode 的成功率。三个种子中有一次成功就把整题算成功，是另一种统计方式，不能把它拿来替换当前指标。

96 条轨迹来自 32 个变体、14 个原题来源。重复采样与同源变体存在相关性；如果后续估计置信区间，应考虑按 source_id 聚类，而不是假设有 96 道独立题。

### 6.3 配对结果保留了退化信息

相同 task/seed 下，62 条仅 SFT 成功、1 条仅 Base 成功、1 条同时成功、32 条同时失败。完整记录既能展示收益，也能定位退化和持续失败。

例如 `mbpp-548-m02 / seed43` 是 Base 成功而 SFT 失败的样本。`mbpp-526-m01 / seed17` 中，SFT 已调用真实测试，看到公开测试 0/2 后仍结束，私有验收只过 2/7。动作合法与利用反馈继续修复是不同能力。

### 6.4 训练成功与能力提升的证据不同

| 证据 | 可以支持的结论 | 仍不能单独支持的结论 |
|---|---|---|
| 命令退出码 0 | 进程正常结束 | 参数真的发生有效变化 |
| 有限非零梯度 | 优化路径产生了梯度 | 梯度来自有效相对奖励、模型能力提高 |
| 相对 SFT 的权重变化 | GRPO 阶段产生了新参数变化 | 开发集或测试集收益 |
| checkpoint 可重载 | 模型产物可使用 | 修复成功率提高 |
| Base/SFT-only 完整 dev 对照 | 当前 dev 协议下的 SFT 前后变化 | GRPO 的新增收益、最终 test 表现 |
| 未来 SFT-only/SFT+GRPO 同协议对照 | 在该评测范围内判断 RL 增量 | 未运行的最终独立测试结论 |

### 6.5 资源与保存也属于实验设计

SFT 用 LoRA 降低可训练参数与优化器开销；第八天 GRPO 则使用合并模型做全参数更新。梯度 checkpoint 通过重算降低激活保存开销，offload 把参数或优化器状态移到 CPU，代价是计算或数据搬运。模型 checkpoint 是磁盘保存产物，和梯度 checkpoint 是两个概念。

本次单卡 FSDP 使用 NO_SHARD，不能写成多卡分布式经验。首步后约 100.8 秒/update 只适用于本次 4 题、n=4 的配置，不含初始化和导出，不能直接作为正式训练耗时承诺。

smoke 保存 model 和 extra，没有 optimizer 状态。它支持重新加载模型，不支持精确恢复优化器继续原训练。第八天结束时数据盘剩余约 4.4GB，这是当时记录；正式训练前要重新体检并安排存储。

## 7. 问题、原因与解决过程

以下区分已观察到的问题、已处理的接口风险和仍未解决的能力问题，避免把设计要求全部描述成实际发生过的故障。

| 问题或风险 | 原因与证据 | 实际处理 | 学习要点 |
|---|---|---|---|
| 原模型写入占位符或散文 | 第七天 37 次写入请求无成功，33 次源码拒绝 | 保留原始失败，验证接口后增加 train 轨迹 SFT | 先查失败类型，再决定是否训练 |
| 同题候选全部为 0 | 原模型诊断没有相对奖励差异 | SFT 后相同条件复测，train 2/4 组出现差异 | 运行正常不等于有学习信号 |
| 工具输出与模型输出混淆的风险 | 训练 response 如果包含观察，会污染策略目标 | 按生成 step 分行，观察进入下一轮 prompt，检查原始 token 和 mask | 数据编码是算法正确性的一部分 |
| 终局奖励重复计入的风险 | 给每步都加成功奖励会偏向更长轨迹 | 核对各步即时奖励和轨迹总奖励，真实 batch 检查重复计分 | 奖励只计一次，优势可广播多步 |
| 接口测试无法代表真实优化路径 | 第七天脚本探针并未使用 vLLM 自主生成 | 第八天保存真实多轮轨迹，在实际优化器前检查 batch | 单测、探针和训练实测各有边界 |
| dev 评测启动报属性错误 | RepairTask 没有 split 属性，split 在任务元数据中 | 改为读取元数据字段；任何评测 episode 产生前修正 | 对齐数据模型，不把程序错误算模型失败 |
| Hydra 拒绝字典参数 | 命令行中带引号字典键不符合该解析路径 | 改为逐个配置键传入 runtime env，并先解析完整配置 | JSON 能解析不等于配置框架能解析 |
| 第五次 pg_loss=0 但梯度非零 | 分组全 1，策略优势为零，KL 项仍有梯度 | 同时记录奖励差异、策略损失、KL 和梯度 | 不凭单个日志指标下结论 |
| 合法动作仍修复失败 | SFT dev 动作合法率 100%，仍有失败与无效源码 | 分层统计解析、契约、写入和终局验收 | 格式能力与任务能力分开评估 |
| 模型看到公开测试失败后直接结束 | 已保存的 mbpp-526 等轨迹 | 当前保留为持续失败，尚未解决 | 成功教师轨迹并不充分教授失败后恢复 |
| checkpoint 与备份范围容易误解 | 第七天本机有 adapter；第八天完整权重仍在远端，未保存 optimizer | 记录模型位置、SHA256 和保存内容 | adapter、完整权重、完整续训状态分别核对 |
| 正式训练存储不足 | 第八天结束记录仅余约 4.4GB | 已记录，正式训练前仍需处理 | 存储与保存策略要先于长训练规划 |

对于仍未解决的反馈利用问题，后续可以考虑收集“失败测试 → 再修改 → 再测试”的有效 train 轨迹，并通过正式 RL 与对照评测观察变化。这是后续方向，当前没有证据保证某一种处理一定改善。

## 8. 面试问题与回答参考

以下答法应在自己能解释源码和数据后使用；具体个人贡献按实际参与情况说明。

### 1. 第 7–8 天最核心的工作是什么？

把自建受限代码修复环境接进 Agent-R1，并完成工具与修复轨迹 SFT、完整 Base/SFT-only dev 基线、5 次真实多轮 GRPO 更新。通过实际 batch 检查、权重比较和 GPU 重载证明了训练链路，但尚未评测 GRPO 的能力增益。

### 2. 这个项目怎样体现 Agent 训练，而不只是一般问答微调？

模型根据需求、当前源码与工具反馈生成下一动作，训练样本是多轮工具交互轨迹，奖励来自最终修复是否通过代码验收。优化对象仍是语言模型参数，工具和环境实现保持固定。这是针对 Agent 行为的模型后训练。

### 3. 为什么不直接从原模型做 GRPO？

先做了原模型诊断，32 条有效轨迹全失败，且大量动作或源码载荷不正确。接口与 Docker 验证正常后，采用计划中的小规模 SFT 备选路线；相同条件复测才出现组内奖励差异。原因来自轨迹证据，不是默认所有 Agent 都必须先 SFT。

### 4. 315 个 SFT 样本是怎么来的？

63 个 train 任务各有 5 个教师决策，每个决策用当时完整上下文预测下一条 assistant 响应，因此得到 315 个监督样本。它们来自 27 个来源，排除了全部诊断来源，不能描述成 315 道独立题。

### 5. 你做的是纯工具格式 SFT 吗？

不是。标签包括读取、写入、测试和结束动作，也包括正确 train 修复源码。改善可能同时来自协议学习和修复行为监督，因此保留 SFT-only 对照，并避免把收益直接归因于 RL。

### 6. 为什么 prompt 的 labels 要设为 -100？

prompt 和已有工具反馈是条件，本次要监督的是下一条 assistant 响应。设为 -100 排除这些位置的监督损失，但模型仍通过 attention 读取它们；标签屏蔽与删除上下文不同。

### 7. 第七天和第八天都用 LoRA 吗？

第七天是 rank=16 的 LoRA SFT，随后合并模型。第八天从合并权重做全参数 GRPO，实际配置 lora_rank=0。两阶段使用的优化方式不同，不能统称为 LoRA 强化学习。

### 8. 梯度累积 4 与 rollout.n=4 有什么区别？

前者表示累计 4 个 micro batch 的梯度后更新一次，用于组织监督训练计算；后者表示同题生成 4 条候选轨迹，用于相对奖励比较。数值相同，但作用、数据单位和训练阶段不同。

### 9. 多轮工具反馈参与训练了吗？

反馈作为下一轮 prompt 的条件，影响后续动作与梯度计算。反馈文本本身不作为模型生成的 response 来计算策略损失。当前每轮生成单独形成一个训练 step。

### 10. 为什么不能先把 JSON 改写漂亮再保存成 response？

训练概率应该对应模型实际生成的 token。执行解析可以严格解释允许的包装格式，但不能把执行端改写的另一段文本冒充原始策略动作。本项目保存原始生成、response_ids 和 mask，并检查上游 padding 没有改写它们。

### 11. 只有最后一步得到 1，前面步骤如何学习？

上游先按整条轨迹汇总奖励，再在同题候选之间计算优势，广播到该轨迹各步的生成 token。即时奖励仍只在终局计一次。这个方法提供轨迹级信用分配，并不精确区分每一步的因果贡献。

### 12. 能手算一组 GRPO 优势吗？

本实现对 `[1,1,0,1]` 使用样本标准差：均值 0.75、标准差 0.5，加入很小 epsilon 后，优势近似 `[0.5,0.5,-1.5,0.5]`。若全部为 0 或全部为 1，优势都为零。

### 13. 没有 Critic，为什么还有 reference？

Critic 估计价值；本次 GRPO 用同题候选的相对奖励构造优势，不训练价值 Critic。reference 仍用于 KL 约束，奖励仍由验收器提供，三者职责不同。

### 14. 为什么第五步损失为零还发生参数更新？

准确说，第五步的策略损失 pg_loss 为零，并不是所有损失为零。当时所有分组全成功，策略优势为零，但 KL 项非零，所以仍有很小梯度。分析时必须分清各损失分量。

### 15. 怎样证明真实多轮轨迹进入了优化器？

保存 80 条实际 vLLM 轨迹，在实际 `_update_actor` 前读取 batch，核对各轨迹步骤、同题分组、环境总奖励、mask 和实际优势。训练后有恰好 5 条更新指标，并与对应 trace ID 对齐；不是只用脚本调用工具或官方数学样例证明。

### 16. 怎样处理执行服务故障？

故障不能当作模型普通零奖励。当前训练实现抛出异常并终止该 rollout/batch；完整评测按原 seed 最多重试 2 次。未实现选择性训练恢复时，不删一条候选就继续计算不完整分组。

### 17. train 的参考答案上传到 GPU，算不算泄漏？

train 正确答案作为 SFT 监督标签是训练数据的一部分。关键是 dev/test 标签不参与训练、诊断来源按 source_id 排除，并且候选工具工作区不提供参考答案和私有验收材料。公开 MBPP 的来源隔离只约束本次后训练划分，不能保证基座预训练从未接触这些公开题目。

### 18. 2.08% 到 65.63% 应该怎样介绍？

这是冻结的 32 个 dev 变体、14 个来源，每题 3 seeds，所有有效单次 episode 的 Base/SFT-only 成功率。可以介绍为当前 dev 协议下的 SFT 前后观察，不能说成 GRPO 提升、pass@3、最终测试成绩或 96 道独立题。

### 19. 为什么第七天 75%，第八天变成 65.63%？

第七天只测少量任务、4 次采样、temperature=0.8；第八天是完整 dev、3 次采样、temperature=0.6。任务范围与采样协议不同，不能仅看这两个百分比判断退化。

### 20. 训练 reward 到 100%，是否说明已经训练成功？

第五次只重复评测 4 个 train 任务的本批候选，全部成功不代表开发集或独立测试表现。同时全 1 分组缺少相对学习信号。本日训练链路验收通过，效果结论仍需要完整 SFT-only/SFT+GRPO 对照。

### 21. 为什么还要与 SFT 起点比较权重？

若只与 Base 比较，之前的 SFT 变化也会被算进来。与 SFT-only 比较后确认 282 个张量、约 6935 万个元素发生新的变化，并验证导出后 BF16 重载仍保留差异，才能把这部分参数变化归到本次训练阶段。

### 22. checkpoint 能重载，是否就能精确续训？

不能。本次 smoke 只保存 model 和 extra，没有 optimizer 状态。精确续训还需按框架核对优化器、学习率调度、随机状态、数据进度等；换硬件后也不能保证逐 bit 重现。

### 23. SFT 后还有什么不足？

动作契约合法率提高不等于真正利用反馈。存在公开测试失败后直接 final、私有验收未通过的轨迹，且有一个 Base 成功、SFT 失败的配对样本。后续要保留这些案例，验证迭代修复行为，而不是只报平均成功率。

### 24. 与 ZzhClaw 怎样结合？

训练环境提供受限修复协议与模型权重，后续在 ZzhClaw 增加相同工具、提示词和预算的 profile，再做应用端对照。模型导出、API 可调用和工具语义一致需要分别验证；当前还没有完成回接，不能说已上线到 ZzhClaw。

### 25. 这两天最值得讲的工程取舍是什么？

先保留原模型失败，再用来源隔离的 SFT 解决探索不足；独立记录 SFT-only 基线；在真实优化器前检查轨迹、奖励与优势，最后核验权重和重载。这让问题定位与结论归因都有可检查的证据。

### 10.2 当前阶段可用的简历条目

- 基于 Agent-R1 接入受限代码修复 AgentEnv/Flow，以 Docker 隔离执行候选，区分公开测试反馈、终局私有验收与基础设施失败；核验多轮轨迹的生成 token mask 和奖励传递。
- 构建 63 个 train 任务的 315 个工具与修复监督样本，完成 1.5B 模型 LoRA SFT；在冻结的 32 个 dev 变体、14 个来源、每题 3 seeds 下，单次修复成功率由 2.08% 提高至 65.63%。
- 完成自建环境 5-update 全参数 GRPO smoke，80 条真实多轮轨迹参与更新；实际 batch 分组与优势检查、相对 SFT 起点的权重变化、HF 导出及 GPU 重载通过。

这是当前阶段表述，不等于完整项目已经交付。不能写“GRPO 将成功率从 2.08% 提升至 65.63%”“独立 test 达到 65.63%”“已在 ZzhClaw 上线”“完成多卡训练”或“支持精确断点续训”。
