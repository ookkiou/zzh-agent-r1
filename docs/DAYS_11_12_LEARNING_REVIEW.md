# 第 11–12 天学习总结：选定模型、冻结评估与独立测试

项目：基于 Agent-R1 的 Python 代码修复 Agent 训练，配套 ZzhClaw。

报告整理日期：2026-10-21。第 11、12 天指执行计划的阶段，不是新增的两个自然日。本文依据实际代码、冻结文件与完成报告回顾；本次只整理材料，没有重新训练或运行模型。

**这两天完成的核心工作，是从“训练跑过”走向“用公平、可追溯的实验判断训练结果”。**第十一阶段用冻结 dev 评估并选定 checkpoint70；第十二阶段在模型和规则固定后，构建、验收并运行独立 test。

最终 test 中 SFT-only 为 **90/126（71.43%）**，SFT+GRPO step70 为 **93/126（73.81%）**，观察差异为 **+2.38 个百分点**。这是小规模、受限修复任务上的结果，未做统计显著性检验，不能声称通用 Agent 能力得到稳定显著提升。

代码开发、排障和报告整理有编码助手协助。下文区分“项目已经完成的证据”与“你应该能独立解释的知识”，脚本运行成功并不自动等于已经掌握。

## 1. 第十一阶段：我们实际做了什么

### 1.1 先确认训练状态，再决定评估对象

| 事项 | 实际状态 | 应如何理解 |
| --- | --- | --- |
| 原训练计划 | 最多累计 225 次更新 | 是计划上限，不是已经完成的步数 |
| 实际完成更新 | 到第 74 步 | 不声称执行了第 75 次更新 |
| 停止触发 | 第五个连续无组内奖励差异的 batch，保护在更新前触发 | 提示相对学习信号不足，不等于证明模型收敛 |
| 最近完整 checkpoint | 第 70 步 | 第 71–74 步没有保存到候选模型 |
| 优化器状态 | 不保存 Adam 动量 | 恢复后重建优化器，不是不中断训练的精确延续 |
| 评估决定 | 先导出、测试 step70，不立即重启 GRPO | 用已有候选获得效果证据，再考虑下一轮实验 |

同题采样的奖励全为 1 或全为 0，都没有组内相对排序信号。全为 1 的 batch 可以成功率很高，但相对优势为零；KL 项仍可能产生梯度，因此“参数仍在更新”和“仍有有效相对奖励信号”也要区分。

### 1.2 导出模型并检查身份

FSDP 训练 checkpoint 与直接用于推理的 Hugging Face 目录用途不同。使用固定版本的 verl merger，将 `global_step_70/actor` 导出为完整 HF 权重、配置、tokenizer 和 chat template。

导出后使用 `/root/zzh-day9-eval/merged-step70`，并检查两模型的 tokenizer、特殊 token 和生成默认配置一致。评估前计算导出 `model.safetensors` 的完整 SHA256，用于绑定实际评测的模型。

原 FSDP checkpoint 的检查主要是完成标记与文件大小；不能把“导出模型已经做完整哈希”写成“所有源分片都重新做完整哈希及重载验收”。这是两个检查范围。

### 1.3 冻结 dev，比较同一个 SFT 起点

公平对照为 **SFT-only vs SFT+GRPO step70**。如果用 Base 对最终模型，观察变化会混入 SFT 的贡献，无法把差异都归给 GRPO。

沿用已有 32 个 dev 任务、14 个原题来源，每题 seeds 17 / 29 / 43，各模型 96 条单次 episode。虽然训练集从 72 扩充至 300，但逐项检查 dev 的 starter、公开测试及模型可见消息没有变化；其中 starter 与公开测试共 64 个文件逐字节一致。

| dev 指标 | SFT-only | step70 |
| --- | ---: | ---: |
| 成功 / 有效 episode | 63/96 | 72/96 |
| 成功率 | 65.625% | 75% |
| seed17 | 19/32 | 24/32 |
| seed29 | 23/32 | 24/32 |
| seed43 | 21/32 | 24/32 |

差异 **+9.375 个百分点**。同题同 seed 配对：改善 11、退化 2；按 14 个来源汇总，5 个改善、1 个退化、8 个持平。

这些结果支持将 step70 固定为下一阶段候选，但没有比较所有训练步数，不能称它为全局最优 checkpoint。

### 1.4 在 test 之前冻结候选

`reports/day11_candidate_freeze.json` 固定了候选 step、导出权重哈希、SFT 基线哈希、训练身份、dev 协议及选择依据。冻结时 test 任务尚未生成，模型 test 尚未执行。

该文件后续作为不可变输入被 test 协议绑定。里面的 `test_executed=false` 是**冻结当时的历史事实**，不能在 test 完成后为了“更新状态”直接修改；当前完成状态应看最终验收报告。

## 2. 第十二阶段：我们实际做了什么

### 2.1 从冻结来源构建可执行的 test

早期锁定的 50 个 MBPP 来源，只表示“留出了哪些原题”，不表示已经拥有 50 个完整、可运行、经过验收的修复任务。

实际顺序为：

```text
冻结 step70 候选
  → 固定模型无关的任务构建与排除规则
  → 审查 50 个来源的输入域和输出契约
  → 独立编写公开/私有用例，生成单位置 AST 缺陷
  → 参考通过、缺陷失败的静态与 Docker 验收
  → 封存模型、数据、协议和脚本身份
  → 才运行两个模型的独立 test
```

每个入选来源保留一个缺陷任务。按固定缺陷类别顺序选择第一个能被公开和私有用例都检出的候选，不参考模型能否修复，也不通过换来源补齐数量。

### 2.2 为什么 50 个来源最终保留 42 个

| 来源 | 在模型 test 前确定的排除原因 |
| --- | --- |
| mbpp-133 | 冻结生成器未产生能被两组用例都检出的有效缺陷 |
| mbpp-134 | 题目没有定义重复 p 次的具体操作 |
| mbpp-172 | 参考实现在合法字符串边界上越界 |
| mbpp-248 | 浮点调和和与冻结的严格类型、精确相等比较规则不适配 |
| mbpp-327 | 示例输入违反三角不等式，契约矛盾 |
| mbpp-397 | 示例期望 float，参考实现返回 int，与冻结比较器冲突 |
| mbpp-452 | 题述为亏损，参考实现和示例计算正利润 |
| mbpp-463 | 参考实现在合法的最大乘积子数组边界上错误 |

排除依据是任务本身的可验收性，并非模型失败后删题。完整排除清单属于结果的一部分。审查状态为 `agent_reviewed_not_human_signed_off`，没有冒充人工签字。

### 2.3 先验收题目，再验收模型

| 数据与执行检查 | 实测结果 |
| --- | ---: |
| test 原题数 / 修复任务数 | 42 / 42 |
| 公开测试 / 私有用例 | 84 / 312 |
| 正确实现的公开、私有验收 | 42/42 任务全部通过 |
| 缺陷实现被公开、私有验收检出 | 42/42 任务全部符合要求 |
| 真实 Docker 执行 | 168 次：42 × 正确/缺陷 × 公开/私有 |
| 确定性重建 | 逐字节一致 |
| 新加载边界测试 | 5 项通过 |
| 原服务回归测试 | 12 项通过 |
| GPU 公开导出 | 127 个文件，不含参考、私有用例或缺陷元数据 |

这里的 **42/42 只是数据夹具验收**，不是模型 100% 修复成功。检查题目与比较器能够辨别已知正确/错误实现之后，模型评估的分数才有清楚含义。

### 2.4 保持运行时可见性隔离

GPU 模型侧只收到任务说明、缺陷 starter 和公开测试。模型通过 `read_file`、`write_file`、`run_tests` 与环境交互；私有用例及期望值由 Mac 上的独立服务持有。

最终 test 使用独立的本机 8766 服务与 GPU 18766 反向隧道，和 train/dev 的 8765 / 18765 分开。默认 train/dev 加载器继续拒绝 test，只有显式 final-test 加载器与允许列表可加载封存任务，避免为执行一次 test 而放开原有数据边界。

公开测试反馈可进入模型的下一轮 prompt。私有验收只在终局进行，模型轨迹不包含私有输入、期望值或异常细节；结果报告可保存通过/失败数量等汇总。

### 2.5 封存后进行真实 GPU 对照

两个模型使用相同的原始任务、同一套工具、消息格式、tokenizer 和生成默认配置。主要协议如下：

| 设置 | 固定值 |
| --- | --- |
| 模型 | SFT-only / GRPO step70，完整导出权重 SHA256 固定 |
| 推理后端 | Transformers SDPA，BF16，单 episode 顺序生成 |
| seeds | 17 / 29 / 43 |
| temperature / top_p | 0.6 / 0.95 |
| 每个模型的评估量 | 42 题 × 3 seeds = 126 条 |
| 最大决策次数 | 6 |
| prompt / response 上限 | 4096 / 512 tokens |
| episode / 单次测试超时 | 240 秒 / 10 秒 |
| 模型失败 | 保留，不重新抽样直到成功 |
| 基础设施失败 | 单独记录，按协议最多重试 2 次；本次实际为 0 |

检查输入通过只说明“准备好执行”；只有两模型各 126 条有效 episode、各自 complete 和 comparison.complete 都为 true，才能报告本次完整 test 结束。

## 3. 最终 test 结果：具体说明了什么

| 指标 | SFT-only | step70 |
| --- | ---: | ---: |
| 成功 / 有效 episode | 90/126 | 93/126 |
| 成功率 | 71.429% | 73.810% |
| seed17 | 31/42 | 31/42 |
| seed29 | 30/42 | 31/42 |
| seed43 | 29/42 | 31/42 |
| 基础设施无效尝试 | 0 | 0 |

两模型合计 **252 条有效 episode**。成功数净增 3，成功率差值约 **2.381 个百分点**；这是百分点，不是把相对百分比增长写成同一个数字。

### 3.1 为什么要看配对，而不只看两个总数

相同任务、相同 seed 的两条 episode 组成一对。完整配对情况为：

| 配对情况 | 冻结 dev | 独立 test |
| --- | ---: | ---: |
| 两模型都成功 | 61 | 86 |
| SFT 失败、step70 成功 | 11 | 7 |
| SFT 成功、step70 失败 | 2 | 4 |
| 两模型都失败 | 22 | 29 |
| 合计 | 96 | 126 |

因此 test 的净增 3 来自 **7 次改善 − 4 次退化**，不是“只有三条发生变化”，也不是“其他任务完全没有退化”。

### 3.2 为什么不能说模型已被证明普遍提升

- 126 条 test episode 来自 42 个原题，每题重复 3 seeds，并非 126 道独立原题。
- 同题重复运行相关；dev 还包含同一原题的不同缺陷变体。不能把所有 episode 当相互独立样本，直接计算很窄的置信区间。
- 当前没有做统计显著性检验；小幅正差异不等于已经证明稳定收益。
- 任务是 MBPP 来源的单文件修复、三个工具和六次决策，未测任意真实代码仓库、完整通用工具集或多文件长任务。
- train/dev/test 来源隔离不等于排除了预训练模型曾接触公开 MBPP 的可能性。
- 此对照评估的是整个 SFT → GRPO 增量方案；没有做额外数据量、训练预算或反馈机制的严格消融，不能证明某个具体机制是收益来源。

dev 的 +9.375 pp 与 test 的 +2.381 pp 都应报告。差异变小可能涉及来源难度、开发集选模、采样等因素；当前证据不足以把原因单独归结为过拟合，也不能删除较小的 test 收益。

## 4. 应该建立的知识框架

| 层次 | 核心问题 | 这两天对应的知识 |
| --- | --- | --- |
| 训练状态 | 更新到哪里，保存到哪里？ | optimizer update、checkpoint、未保存更新、停止保护 |
| 模型资产 | 哪份权重被评估，能否再次使用？ | FSDP 与 HF 导出、tokenizer、SHA256、备份 |
| 实验设计 | 与谁比，哪些条件相同？ | SFT 对照、固定预算、生成后端、种子与配对 |
| 数据有效性 | 题意和答案是否自洽？ | 输入域、类型契约、mutation、参考与缺陷验收 |
| 数据隔离 | 哪些内容能进入模型？ | source_id 划分、公开导出、私有用例服务、显式加载边界 |
| 测量与统计 | 分数的单位是什么？ | 原题/变体/episode、单次成功率、pass@3、相关样本 |
| 可追溯性 | 如何复查和排查？ | 不可变候选、封存协议、原始轨迹、来源哈希与失败记录 |
| 工程交付 | 成绩和模型是否都已保留？ | 小报告、完整权重、实例内保留与实例外备份 |

dev 用于决定下一步实验；test 用于在模型与规则已经固定后独立报告。只要把 test 反馈用于后续改提示、改训练或挑 checkpoint，它就进入开发过程，后续新结论应使用新的独立留出集或明确标记为探索性结果。

### 单次成功率与 pass@3

本项目的指标是 `所有有效单次 episode 的成功数 / 有效 episode 总数`。42 题 × 3 seeds 的分母为 126。

“一题三次只要有一次成功就算该题成功”的汇总方式是另一个指标，不能把它混称为本项目已报告的单次成功率，也不能将本次 93/126 写成 pass@3。

## 6. 面试可能会问的问题

### 1. 你为什么没有直接训练到 225/255？

225 是原方案上限。实际连续五批缺少组内奖励差异，保护在第 75 次更新前停止；完成到 74、完整保存到 70。我们先对 step70 进行冻结 dev 和独立 test，而不是用步数当效果证据。

### 2. 70 步是最好的 checkpoint 吗？

没有证据证明。它是当时最新完整保存的候选，在冻结 dev 上相对 SFT 有正向差异，因此在 test 之前固定下来；没有系统比较所有 checkpoint。

### 3. 为什么基线是 SFT-only，而不是原始 Base？

正式 GRPO 从 SFT 权重开始。比较 SFT-only 与 SFT+GRPO 能观察增加这段训练方案后的结果；Base 对最终模型会混入 SFT 贡献。

### 4. 测试中的 126 是 126 道题吗？

不是，是 42 个原题各运行 3 个 seeds，共 126 条单次 episode。重复种子并非独立原题，不应夸大样本数量。

### 5. 为什么来源从 50 变成 42？

八个来源在任何模型 test 前因契约矛盾、参考错误、类型比较冲突或无有效缺陷被排除；规则与清单留档，不根据模型成败选择题目，也没有补入新来源。

### 6. 怎么证明模型成绩不是参考答案泄漏？

GPU 只收到说明、starter 和公开测试。参考与私有用例不在公开包中，私有验收通过独立服务执行；来源按原题隔离。此证明针对本次训练/运行路径，不保证公开预训练语料完全没有该题。

### 7. 只提高三个成功，有什么意义？

我们如实报告小幅观察差异，不把它包装为显著突破。配对为改善 7、退化 4；当前价值还包括可追溯的训练、执行、评估闭环。是否稳定有效，需要更多独立来源及不确定性分析。

### 8. seed17 两模型都 31/42，是否输出完全相同？

不能这样推断。总成功数相同不代表逐题结果、补丁或工具轨迹相同，需要对相同 task/seed 进行逐条配对检查。

### 9. 正确实现 42/42 通过，为什么模型不是 42/42？

前者验证题目和执行器是否能判别已知正确实现；后者要求模型从缺陷出发自主生成正确补丁。两者验收对象不同。

### 10. 会不会公开测试通过，但私有测试失败？

会。公开反馈帮助模型开发补丁，私有用例覆盖额外边界。终局成功按冻结的私有验收定义，不把只通过公开测试当作最终成功，也不能用私有反馈反复引导模型修改同一条 episode。

### 11. 以后训练到 255，再测这份 test 行不行？

可以作为后续对照或探索记录，但已看过的 test 若参与决策，就不能继续当全新盲测。应该在新实验开始前固定方案，保留这次结果；更强的独立结论需要新的未使用留出来源。

### 12. FSDP checkpoint 和 HF 模型哪个要保留？

推理需要完整 HF 目录；继续训练还需要源 checkpoint 及身份、小状态、代码/数据/配置指纹。当前 checkpoint 不含 Adam 动量，续训路径会改变。模型哈希、报告或 `.partial` 下载不能替代完整权重。

## 7. 如何确认自己真的掌握了

建议不看答案完成以下练习，再对照报告核对：

1. 画出“训练停止 → 完整 checkpoint → HF 导出 → dev 选候选 → test 封存 → 独立 test”流程，说明每步验收对象。
2. 用纸笔算出 63/96、72/96、90/126、93/126 的成功率与百分点差值，并用改善/退化解释净增。

## 8. 能怎样写进项目介绍

可以说：

> 在固定工具与预算下，以 SFT-only 为对照评估 GRPO checkpoint70；先冻结 dev 协议与候选，再基于预留来源构建并验收独立 test。42 题 × 3 seeds 共 252 条双模型有效轨迹中，成功数从 90/126 到 93/126，约 +2.38 个百分点，配对改善 7、退化 4；保留数据排除、失败和停止记录。

后续第 13–14 天的 ZzhClaw / vLLM 应用 dev 为 69/96 → 75/96，是不同后端上的迁移实验；不把它的 +6.25 pp 混入本报告的第 11–12 天结果。
